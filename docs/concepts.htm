Concepts

How the Solution Works

A wizard-style installer is mostly the same window shown five or six different ways: a title bar, a header describing the current step, a body that changes with each step, and Cancel/Back/Next buttons along the bottom whose availability and wording shift as the user moves through the steps. Written directly against AutoIt's GUI functions, that window has to be built and rebuilt by hand for every project, and the button logic - what's enabled on the first page, what the Next button should say on the last one, what happens when the install itself is running - tends to get copied from one script to the next with small, easy-to-miss differences each time.

Crucial Setup Wizard turns that window into a small number of building blocks. A script builds one configuration map describing sizes, fonts and captions, hands it to _NewWizard() to get a window with a header and a button row already in place, and then adds pages to it - either from a set of five ready-made templates covering the common steps, or from scratch when a step needs something the templates don't cover. Each page declares what kind of step it is (an ordinary page, a final confirmation, a busy page, a finishing page), and the wizard reads that declaration to decide on its own what the buttons should look like and do, so that logic never has to be written twice.

Underneath the pages, a small event mechanism lets a page or a button run a piece of the caller's own code at a specific moment - when the page appears, right after it appears, when it's about to close, or when a particular button is clicked - without the wizard's own navigation code needing to know what that code does. That's the mechanism a progress page uses to run the actual install routine and move on once it's done, and the one a folder-picker page uses to open a browse dialog when its button is clicked.

The Installer Config

_NewInstallerCfg() produces the one map, $mCfg, that every other public function expects. It is assembled from three smaller pieces - window size and layout (_NewWndCfg()), font (_NewFontCfg()), and button dimensions and captions (_NewBtnCfg()) - flattened into a single map so that a page template needing, say, a Y position from one piece and a caption from another can read both from the same argument:

Local $mCfg = _NewInstallerCfg(_NewWndCfg(640), _NewFontCfg("Segoe UI", 12))

Because it is an ordinary map, a single value can be changed after the fact without rebuilding anything - overriding $mCfg.sBtnCaptApply to turn "Install" into "Uninstall" for a companion uninstaller is a common example, shown later in Getting Started.

A Page's Status Decides Its Buttons

Every page is a map, created by _NewPage() and usually added to the wizard through one of the _Add*Page() template helpers rather than by hand. Each page carries an iStatus value that tells the wizard what kind of step it represents, and the wizard uses that value - together with whether the page happens to be first, last, or somewhere in the middle - to decide what Cancel, Back and Next should look like the moment the page becomes current:

  • $eNormalPage. An ordinary step; Next carries its usual caption.
  • $eProceedPage. The step just before doing the real work; Next switches to the configured Apply/Install caption.
  • $eProcessingPage. Work is underway; Cancel, Back and Next are all disabled so the user can't interrupt or repeat it.
  • $eFinishPage. The last step; Next switches to Finish and Cancel/Back are disabled.

None of this needs to be wired up by the calling script - it falls out of picking the right page template, or setting iStatus directly on a hand-built page.

Hooking Into a Page's Lifecycle

A page can react to five moments: OnLoad and AfterLoad as it becomes the current page, OnLeave when the wizard move from one page to another, OnClose as the wizard is about to exit from it, and OnClick on any button that isn't Cancel, Back or Next. Each hook is a small map built by _SetEventHandler(), pairing a function reference with an optional list of arguments from _HandlerArgs():

$mPage.AfterLoad = _SetEventHandler(_AfterLoad_FinishPage)
_SetPageBtnOnClickEvent($mPage, $idBtnBrowse, _SetEventHandler(_OnClick_SetFolder, $aArgs))

This is what lets a progress page run an arbitrary install routine on AfterLoad and click Next automatically once it returns, and what lets a folder-picker page open a browse dialog when its own button is clicked - all without the wizard's navigation loop needing a single line of code specific to either one.

Templates, and Building a Page Without One

The five _Add*Page() functions - intro, path, ready, progress, finish - are what most scripts call directly. Each one creates its controls, sets the page's status and subtitle, wires up whatever event handler it needs, adds the page to the wizard, and remembers its index on the wizard map ($mWizard.iReadyPageId, and so on) so it can be looked up again later. When a step doesn't fit any of the five, the same pieces are available individually: _NewPage() to create it, ordinary GUICtrlCreate* calls plus _SetPageCtrl() to add and register its controls, and _SetPageBtnOnClickEvent() to wire up any button on it.

How Failures Are Reported

Functions that validate their own input - a window handle, a config map, a wizard map, a control reference - follow one convention throughout the library: on invalid input they call SetError() with one of the $INST_ERR_* codes and return a safe value, usually Null or 0. Check @error after _NewWizard() or any _Add*Page() call rather than assuming it succeeded:

Local $mWizard = _NewWizard($mCfg, "Lumen Setup", "Lumen")
If @error Then
    ; $mCfg was not a valid installer config
    Exit
EndIf

While a script is still being run directly from the editor (rather than compiled), the same failures are also written to the console as a readable message naming the function and the problem, which is usually enough to spot a bad config or a stale control ID without attaching a debugger.
